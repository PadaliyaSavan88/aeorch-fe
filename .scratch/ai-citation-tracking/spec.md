# AI citation tracking (real implementation, replacing the dummy preview)

Status: ready-for-agent

## Problem Statement

The report page (`/report/[id]`) has always shown an "AI Citation Tracking" section, but it has never measured anything real — it renders 12 fixed bars with the first 3 hardcoded as "cited," labeled "Preview," with copy that says this is an upcoming feature. There is no backend support at all: no model, no endpoint, no LLM-API integration anywhere in the codebase. Users (and agencies reporting to their clients) cannot actually find out whether an AI answer engine mentions their site, which is the core promise implied by both the product's AEO positioning and this section's own copy.

Separately, the feature as originally placed doesn't fit its own nature: it's scoped to a single one-off Scan, but "does an AI model cite this site" is something that changes over time and is naturally checked on a recurring cadence, which fits the existing Site/Organization model (and its Tracking Scan precedent) far better than the per-Scan report.

## Solution

Build a real, recurring Citation Check feature scoped to a `Site` within an `Organization`, gated to the `agency` plan (matching the existing Tracking Scan precedent of "org-level recurring features are an agency-tier benefit"):

- A new backend job, scheduled like the existing `creditReset` cron, finds Sites due for a check (weekly cadence) and runs each one through a queue worker (mirroring the existing `scan-queue`/`scan.queue.ts` pattern).
- Each check auto-generates a small set of prompts from the Site's most recent completed Scan (brand name, industry/category signals already crawled — no new crawl, no user authoring required for v1), sends each prompt to the user's existing Gemma 4 instance running on the same homelab server as the backend itself (a local, same-host call via its Ollama-compatible API), and records whether the response mentions the site/brand.
- Results are stored per-Site (a real `siteId` foreign key, unlike Scan's URL-matching rollups) and surfaced on a new `/agency/citations` page, plus a manual "Run now" trigger.
- The dummy per-scan section on `/report/[id]` is replaced with an honest, org-gated teaser that links to the real feature, since the real feature no longer lives at the Scan level.
- Because the checked model is a self-hosted Gemma 4 instance rather than the actual production ChatGPT/Claude/Perplexity/Gemini engines, all product copy is explicit about what is being measured — this is a deliberate, explicitly-confirmed trade-off (see Further Notes), not a claim that this measures real-world citation by major AI engines.
- The model and the backend/worker run on the same physical homelab server, so this is a local, same-host call — not a network hop, VPN, or public endpoint to secure. The integration still treats the model service as something outside this project's deployment/lifecycle management (it's the user's own long-running Gemma 4 instance, not spun up by this codebase) and handles it being temporarily down (e.g. mid-restart) gracefully, but the failure mode to plan for is "process not responding on localhost," not network reachability.

## User Stories

1. As an agency user, I want to see whether an AI model mentions my client's site when asked relevant questions, so that I can report on AI visibility the way I already report on SEO rankings.
2. As an agency user, I want citation checks to run automatically on a schedule, so that I don't have to remember to check manually.
3. As an agency user, I want to trigger a citation check manually ("Run now"), so that I can get a fresh result right after fixing something instead of waiting for the next scheduled run.
4. As an agency user, I want to see which specific prompts were checked and whether each one resulted in a citation, so that I understand exactly what's being measured rather than trusting an opaque score.
5. As an agency user, I want to see citation results trend over time (like the existing score-over-time sparkline), so that I can tell my client whether things are improving.
6. As an agency user managing multiple sites, I want a site selector on the citations page (matching the existing `/agency/competitors` pattern), so that I can review each client's results without leaving the page.
7. As an agency owner/admin, I want citation checking to be included in my `agency` plan at no extra manual cost, so that I don't need to think about a separate credit balance for it.
8. As an agency member (non-owner/admin), I want to view citation results read-only, so that I can see the data without being able to change site configuration (matching the existing `assertOrgAccess` read-vs-admin pattern used for competitor comparison).
9. As a solo (non-org) user, I want the report page to be honest that AI citation tracking isn't available to me yet, rather than showing fabricated data, so that I'm not misled about what my scan actually measured.
10. As a solo (non-org) user, I want a clear path to see what the feature would offer (e.g. a link to create a workspace / learn more), so that the teaser serves as a real upsell rather than a dead end.
11. As a prospective agency customer, I want the citation-check copy to be truthful about which model is being queried, so that I can trust the rest of the product's numbers too (consistent with the project's existing no-fabrication standard from the crawler-fabrication bug fix).
12. As the site owner (developer), I want citation checks to reuse the most recent completed Scan's crawled data for prompt generation rather than triggering a new crawl, so that the feature doesn't duplicate crawling infrastructure or cost.
13. As the site owner, I want a Site with no completed Scan yet to simply not be checked (rather than erroring or fabricating prompts), so that the pipeline degrades gracefully.
14. As the site owner, I want the weekly check cadence enforced by the same kind of dedup-window query already used for Tracking Scans, so that no new credit-ledger plumbing is needed for v1.
15. As the site owner, I want a citation-check queue and worker that follow the existing `scan-queue`/`scan.queue.ts` conventions (BullMQ, in-process worker, try/catch marking a `failed` status), so that the new code is operationally consistent with the rest of the system.
16. As the site owner, I want the "is this site cited" detection logic to be a pure, independently testable function, so that its behavior can be verified without calling a real model in tests.
17. As the site owner, I want the local model endpoint's URL/port and model tag documented as required environment configuration (not a new service this project installs or runs), including what happens when the model service isn't responding, so that the dev/deploy setup instructions stay accurate and a model-service hiccup doesn't take down the rest of the citation pipeline.
18. As the site owner, I want a new domain-modeling ADR defining "Citation Check" and explicitly disambiguating it from the existing `GEO_NO_CITATIONS` rule (which checks the site's own *outbound* links), so that the term doesn't collide with existing vocabulary.
19. As the site owner, I want the admin panel to have basic visibility into citation-check volume (count of checks run, roughly like the existing Revenue/Logs tabs' spirit), so that I can sanity-check the scheduled job is actually running in production.
20. As a future maintainer, I want the self-hosted-model constraint isolated behind a small interface (e.g. "given a prompt, return a response string"), so that swapping in a real hosted API (OpenAI/Anthropic) later — the natural v2 — doesn't require touching the scheduling, storage, or UI layers.

## Implementation Decisions

**Scope and data model**
- New domain term: **Citation Check** — a single scheduled or manually-triggered run of a Site against a small set of auto-generated prompts, checked against a self-hosted model, producing a cited/not-cited result per prompt. Explicitly distinct from the existing `GEO_NO_CITATIONS` rule (which checks the scanned site's own outbound external links) — both `CONTEXT.md` files get this term added, and a new `docs/adr/0002-ai-citation-tracking.md` is written (mirroring the existing `docs/adr/0001-tracking-scans-and-comparison-reports.md`) covering the scope decision, the self-hosted-model trade-off, and the disambiguation from `GEO_NO_CITATIONS`.
- New Mongoose model `CitationCheck`: `organizationId` (ref Organization), `siteId` (ref Site, real FK — unlike Scan, which has none), `status` (`queued`/`running`/`completed`/`failed`), `prompts: [{ prompt, modelResponse, cited: boolean }]`, `score` (cited count / total), `model` (e.g. `gemma4`, recorded per-run so a future model change on the homelab side is visible in history), `source` (`scheduled`/`manual`), `errorMessage`, timestamps. No `report`-style untyped blob — the shape is known up front, unlike a Scan's flexible analyzer output.
- No change to the `Scan` or `Site` schemas themselves. `CitationCheck` reads the latest completed `Scan` for the Site's `url` (same URL-matching approach `organization.service.ts`'s `rollupSite()` already uses) purely to source prompt-generation input; it does not duplicate or store scan data.

**Prompt generation**
- Pure function, given a Site's latest completed Scan report: derives brand name (page title / Organization-schema `name` if present), and 2-3 industry/category signal terms (from headings/meta already crawled). Produces a small fixed-size prompt set (proposed: 3-5 prompts, e.g. "What is a good [category] tool?", "Recommend a [category] for [use case]", "What does [brand] do?") — exact prompt templates are a product-copy decision to finalize during implementation, not fixed here.
- If no completed Scan exists yet for the Site's URL, the Site is simply skipped by the scheduled job (not an error) — mirrors "graceful, not fabricated" handling elsewhere in the codebase.

**Self-hosted model integration**
- New service, isolated behind a narrow interface (`checkCitation(prompt, site): Promise<{ response, cited }>` or similar) so the model backend is swappable later without touching scheduling/storage/UI — directly serves user story 20 (the known v2 path to real hosted APIs).
- Calls the user's existing Gemma 4 instance, already running on the same homelab server as the backend, over its local Ollama-compatible HTTP API (`/api/generate` or `/api/chat`, typically `localhost:11434`) — not a service this project installs, runs, or manages, just an existing local endpoint it calls. Configured via env vars regardless (`CITATION_MODEL_ENDPOINT` for the base URL, `CITATION_MODEL_NAME=gemma4` for the model tag) rather than hardcoded, so the port/address stays a config concern, not a code change, if the homelab setup ever changes.
- Since it's a local call, network reachability isn't a real concern, but the model process itself could still be down or restarting: the client applies a request timeout, and any failure (timeout, connection refused, non-2xx) marks that one `CitationCheck` as `failed` with `errorMessage` set — it does not throw out of the queue worker or block other due Sites' checks in the same scheduled sweep. This mirrors `scan.queue.ts`'s existing try/catch-to-`failed` pattern.
- Citation detection (does the model's response count as "citing" the site): a pure function taking the response text plus the site's brand name/domain, doing a substring/domain-match heuristic. Kept separate from the model-calling code specifically so it's testable without a real model.
- No new LLM-provider API keys, no new SDK dependency (`openai`/`@anthropic-ai/sdk`) — this is scoped to a single HTTP client call against the homelab's Ollama-compatible endpoint, consistent with the "near-zero marginal cost, self-hosted" reasoning behind this choice.

**Scheduling and queue**
- New `node-cron` job (mirrors `src/jobs/creditReset.ts`'s structure exactly: schedule string, started from `App.init()`), running daily, querying Sites belonging to `agency`-plan Organizations whose most recent `CitationCheck` (if any) is older than the check interval (proposed: 7 days, same dedup-window shape as `TRACKING_SCAN_DEDUP_WINDOW_MS`) or has none yet.
- Due sites are enqueued one-by-one onto a new BullMQ queue (`citation-queue`, same `redisConnection` as `scan-queue`, defined in `src/config/redis.ts`), consumed by a new in-process `Worker` (mirrors `scan.queue.ts`'s status-transition and try/catch-to-`failed` pattern) — not a BullMQ repeatable job, since the codebase has no precedent for those and the cron-plus-due-query shape already has one (`creditReset.ts`) that fits cleanly.
- Manual trigger: `POST /organizations/:id/sites/:siteId/citations` enqueues a single check immediately (`source: 'manual'`), gated `assertOrgAccess(org, user, {minRole: 'admin'})` — matches the mutation-gating pattern used for site/competitor add. Read routes (`GET .../citations`, latest + history) are open to any member, matching the read-only gating already used for `.../compare`.
- Also fire an initial check right after a Site is added, the same fire-and-forget pattern `addSite()` already uses for `triggerTrackingScan()` — but only if a completed Scan already exists for that URL (see Prompt generation above); otherwise it's simply picked up by the next scheduled cron pass once a Scan completes.

**Access and gating**
- `agency`-plan Organizations only, v1. No solo/non-org access path, no new credit-ledger type or `CreditTransaction` value — the cost story is "included in the agency plan," enforced purely by the cron job's Organization-plan filter, matching how Tracking Scans are already free+uncapped for `agency` orgs. `starter`-plan orgs and solo scans get no Citation Check access in v1 (see Out of Scope).

**Frontend**
- Remove the fabricated `CitationPreview()` bars from `ReportView.tsx`. Replace the section with a small, honest, org-gated teaser: if the viewing user belongs to an `agency`-plan org and the scanned URL matches one of their Sites, link straight to that Site's `/agency/citations` entry; otherwise show a plain "AI citation tracking is available for agency workspaces" note linking to `/agency` (serves user stories 9-10, replacing dummy data with a truthful, still-useful state — consistent with the project's established "no fabricated fields" rule).
- New `/agency/citations` page, structurally following the existing `/agency/competitors` page: site selector for multi-site orgs, latest result (per-prompt cited/not-cited list), a trend view reusing the existing hand-rolled inline-SVG sparkline pattern (`ScoreSparkline` in `ReportView.tsx`) rather than adding a chart library, and a "Run now" button calling the manual-trigger endpoint.
- Sidebar: new "AI Citations" nav item under the agency section, following the existing item pattern (no "Preview" badge, since this ships as a real feature — unlike the earlier `agency-preview` naming this project deliberately moved away from).
- New shared types for `CitationCheck`/prompt-result shapes, added alongside the existing inline report types in `ReportView.tsx` or promoted to a small shared types file if the new page needs to share them across two components — implementer's call at build time, not fixed here.

## Testing Decisions

- Backend: new Jest+Supertest file for the citation controller/routes, following the existing one-file-per-controller convention — covers the full 401/403/2xx matrix (unauthenticated, wrong-org member, owner/admin-only manual trigger, read access for any member) matching the pattern already established for Organization/Competitor routes.
- Prompt-generation and citation-detection are both pure functions — unit-tested directly with fixed inputs/expected outputs, no mocking needed. This is the primary test surface, since it's the actual logic that determines correctness (does "cited" mean what we say it means) independent of any real model.
- The homelab HTTP call is mocked in tests (no real model call, and no dependency on the homelab being reachable, in CI), following whatever mocking convention the existing crawler-service tests already use for external HTTP calls. A separate test covers the timeout/failure path (mocked timeout/non-2xx) asserting the `CitationCheck` ends up `failed` with an `errorMessage` rather than throwing.
- The cron/due-query logic (which Sites are due) is tested as a plain function over seeded `CitationCheck`/`Organization`/`Site` fixtures, not by actually waiting for a cron tick — mirrors how the existing Tracking Scan dedup window would be tested.
- Postman collection: new Citations folder added, mirroring the existing Competitors folder's structure and its reuse of `{{userToken}}` as an outsider identity to stay within the register-rate-limit budget.
- Manual/E2E: a live check against a real Site with a completed Scan, calling the actual local Gemma 4 endpoint, confirming a `CitationCheck` document is created with plausible per-prompt results and that `/agency/citations` renders it correctly in both themes — same verification bar already applied to the PDF-export and Organization-model work (checking actual output, not just HTTP 200). Also manually verify the failure path by stopping the local model service (or pointing the config at a bad port) and confirming the check fails gracefully without affecting other Sites in the same sweep.

## Out of Scope

- Real hosted-API citation checking (OpenAI/Anthropic/Perplexity/Gemini) — the credible v2 once the self-hosted pattern is proven; the model-calling interface is deliberately isolated now specifically to make this an additive change later, not a rewrite.
- User-authored or editable prompts — v1 is auto-generated only, per explicit decision; a prompt-management UI/CRUD is future work if auto-generated prompts prove insufficiently relevant.
- `starter`-plan and solo (non-org) access to real citation checks — v1 is `agency`-plan only. The report-page teaser is the only surface solo users see.
- Any new credit-ledger/`CreditTransaction` type or per-check billing — v1 cost story is "included in agency plan," no metering.
- A configurable check cadence (weekly is fixed for v1) — an org-configurable interval is future work if needed.
- Stripe billing tie-in for this feature specifically — consistent with the standing backlog decision that Stripe work stays last regardless of feature.
- Admin Revenue/Logs becoming citation-aware beyond basic run-count visibility (user story 19) — deeper admin analytics for this feature are out of scope.
- CI wiring for any new verification script beyond the standard `npm test` run — no new script is introduced here, this only concerns the existing test suite structure.

## Further Notes

- The choice of a self-hosted Gemma 4 model over real hosted APIs (OpenAI/Anthropic) was explicitly flagged as a trade-off during scoping and reaffirmed by the user: it avoids per-call API cost and keeps the feature server-runnable on a schedule, but the resulting signal is "does this specific Gemma 4 instance mention this site," not "does ChatGPT/Claude actually cite this site" — a materially different and weaker signal than the feature's name implies at face value. This spec treats that as a deliberate, informed v1 trade-off (not an oversight) and requires the product copy to be explicit about it, consistent with this project's existing hard rule against fabricating data (the crawler-fabrication bug fix, and the "never invent fields" rule from the fix-generators work, are the direct precedent for taking this seriously here too).
- The model is the user's own Gemma 4 instance, already running on the same homelab server the backend itself runs on — this is not a new service the project deploys (unlike, say, the earlier Puppeteer-browser-singleton work for PDF export), and not a network dependency either, since it's a local call. The implementation-time work here is entirely about the local HTTP client (base URL/model-tag env vars, timeout, failure handling), not about standing up, managing, or exposing a model server. `aeorch/CLAUDE.md`'s local-dev section gets a short "Citation checking" entry documenting the required env vars and what happens if the local model service isn't responding — not a new install step, since there's nothing new to install.
- The originally-scoped location for this feature (a per-Scan section on `/report/[id]`) didn't fit a recurring, org-scoped check; moving it to Site/Organization scope means the dummy section's removal from the report page is itself part of this spec's work, not a separate cleanup.
